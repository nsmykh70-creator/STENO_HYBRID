# STENO HYBRID v14

Экспериментальный блочный lossless-кодек C++17. Формат STN13 (не менялся с v13; несовместим с STN9–STN12).

## Что нового по сравнению с v13

- mmap/потоковый I/O: входные файлы (энкод — исходник, декод — архив) мапируются
  read-only (MADV_SEQUENTIAL) вместо копирования в heap-векторы; блоки энкодера —
  read-only указательные срезы маппинга (без по-блочных копий); декод пишет
  распакованные блоки прямо в MAP_SHARED-маппинг выходного файла (размер известен из
  заголовка, файл растёт одним ftruncate). Приватная память (Private_Dirty) на
  корпусе 64 МиБ: энкод 313 → 240 МиБ (−23%), декод 108 → 63 МиБ (−42%); maxRSS
  347 → 324 и 110 → 107 МиБ (страницы маппингов остаются в RSS — это page cache,
  а не heap). При ошибке декода частичный выходной файл удаляется.
- Формат архива не изменился: архивы v14 байт-в-байт идентичны архивам v13
  (проверяется тестом при наличии обоих бинарников).

## Что нового по сравнению с v12

- Обучаемые словари: `steno13 train out.dict samples/ [size=32768]` строит словарь жадным
  выбором самых длинных повторов с маскированием (детерминированно). Энкод `dict=path`
  токенизирует блоки с виртуальным префиксом словаря (дистанции могут ссылаться в словарь),
  плюс mode 1 получает preset-словарь DEFLATE (flag bit1). Словарь хранится ВНЕ архива
  (decode `dict=path`) или встраивается (`embed=1`) — внешние словари выигрывают у
  множества отдельных маленьких архивов: 150 → 81 Б/архив, −45% суммарно на 2000 файлов.
- Дистанционные коды mode 3 расширены до алфавита 50 (дистанции до 2^23 — блок до 4 МиБ
  плюс словарь до 1 МиБ).
- Замечание по применению: внутри одного архива с самоподобным содержимым окно 256 КиБ
  и межблочные словари (v10/v11) уже покрывают повторы — обученный словарь там даёт
  только холодный старт первого блока. Целевой сценарий словаря — множество маленьких
  архивов с общим внешним словарем.

## Что нового по сравнению с v11

- Mode 3 переведён на 4-линейный interleaved rANS: символ k потока идёт в линию k&3,
  каждая линия — независимый rANS; декодер разворачивает 4 независимых обновления
  состояния (ILP ×4) и собирает токены из массивов символов. Потоки симолов получают
  счётчики в payload (проверка курсоров = целостность).
- Оптимальный парсер с ценовой моделью для пресета max (уровень 9 + depth ≥ 2):
  forward-DAG релаксация по блоку (литерал / серия / хеш-цепочки с суб-длинами /
  rep-кандидаты), цены символов из статистики greedy-прохода, rep-кеш следует за лучшим
  путём. На walk-данных mode 3 от DP бьёт greedy на ~11%: walk_fine **14.34%** (v11: 16.25%,
  v10: 19.61%). Для страховки энкодер на max берёт минимум из DP- и greedy-кандидатов.
- Декод mode 3 в зависимости от структуры матчей 150-750 МиБ/с (длинные матчи копируются
  быстро, короткие упираются в побайтовое копирование).

## Что нового по сравнению с v10

- Mode 3: token-поток разбивается на 8 классов (теги, литералы, коды/биты длин, коды/биты
  дистанций, rep-коды, длины серий); классы кодируются rANS order-0 (12-бит вероятности,
  слоты: малые значения напрямую, крупные — бакет + сырые extra-биты). На блоках с
  разнообразными дистанциями mode 3 бьёт mode 2 на ~14%: walk_fine **16.95%** против 19.61%
  в v10 (−13% к размеру архива). Энкодер выбирает минимум из mode 0/1/2/3 на блок —
  регрессий нет. Цена: декод mode-3 блоков ~2× медленнее DEFLATE (однопоточный rANS);
  interleaved rANS — будущая оптимизация.
- Пресеты: `fast` (уровень 2), `default` (6), `max` (9 + depth 16).
- Тесты: 13 roundtrip-корпусов + 11 корпусов с принудительным mode 3 (все блоки через rANS)
  + 14 corruption-кейсов, на обеих сборках.

## Что нового по сравнению с v9

- Rep-коды: кеш последних 4 дистанций, rep-токен `3, varint(code)` (один байт дистанции вместо
  varint до 3 байт). Период 45000 на реальном файле: 4.76% → **2.05%**; синтетика period45k:
  745 → 414 байт.
- Словарь token-потока: mode 2 может использовать хвост (≤32 КиБ) token-потока предыдущего
  блока как словарь DEFLATE (флаг bit1; допустимо только если предыдущий блок тоже mode 2).
- libdeflate (опциональная сборка `-DHAVE_LIBDEFLATE`): тот же raw-DEFLATE, энкод ×1.8–1.9,
  декод ×1.6–1.75. Словарных блоков в libdeflate нет — они по-прежнему идут через zlib
  (формат тот же, декодер dispatch по флагу).
- Параллельный энкод по блокам (std::thread): байты архива идентичны при любом числе потоков.
- Hash-chain depth (CLI `depth`, 1 = поведение v9): на walk-файлах −0.7% к ratio.

Итого на 2 vCPU против v9: энкод ×2.6–3.5, декод ×1.5–1.8, размер −0…−8% (до −57% на периодике).

## Сборка

Требуются g++/clang++ с C++17 и zlib:

```bash
g++ -O3 -DNDEBUG -std=c++17 -Wall -Wextra -pedantic native.cpp -lz -o steno14
# опционально, с libdeflate (быстрее; словарные блоки всё равно идут через zlib):
g++ -O3 -DNDEBUG -DHAVE_LIBDEFLATE -std=c++17 -Wall -Wextra -pedantic native.cpp -ldeflate -lz -o steno14
```

## Использование

```bash
./steno14 encode input.bin output.stn [level=6|fast|default|max] [block=1048576] [window=262144] [depth=1] [threads=0] [dict=path] [embed=0|1]
./steno14 decode output.stn restored.bin [dict=path]
./steno14 train out.dict samples/ [size=32768]
```

Уровень zlib: 1–9 или пресет fast/default/max. Размер блока: 4 КиБ–4 МиБ. Окно: 4 КиБ–4 МиБ.
depth: 1–1024 (глубина цепочки кандидатов). threads: 0 = авто. Декодер определяет формат
по сигнатуре STN13 (I/O с v14 — mmap).

## Важные ограничения

- Это экспериментальная версия, не рекомендуемая для единственного хранения важных данных
  без дополнительных проверок и резервной копии.
- Обработка файла целиком в памяти; потоковый ввод/вывод и mmap — волне 3.
- Парсер жадный с ленивым сопоставлением; это не match finder уровня zstd/LZMA.
- Результаты на синтетических корпусах по 1 МиБ не доказывают преимущество на произвольных файлах.
- Форматы версионируются магией: STN13 не читается декодерами v8–v12.
