# STENO v16 WIP — статус (2026-11-25, сохранено и запушено в GitHub)

## Что сделано и проверено
1. **mode 4** (adaptive binary-tree rANS, 15-битные вероятности, LZMA-счётчики 5 бит,
   контексты: литералы order-1 по выходному байту, теги 2-бит по пред. тегу, слоты общие
   деревья, extra-биты длины/дистанции с ctx=(бакет<<4)|позиция, repv/runv по глубине varint;
   4-lane interleaved; пер-блочная персистентность модели; двухпроходный энкодер:
   модель вперёд + кодер по записям реверсом). Roundtrip OK (fb2 1 МиБ слайс bit-в-bit).
2. **modes 5/6** (rolling tail: mode 3/4 + prefix-словарь из хвоста предыдущего блока,
   cross-block matches, размер хвоста ≤4 МиБ в u32-префиксе payload). Roundtrip OK:
   fb2 45.3 МиБ → 11.46 МиБ (block1M, win1M, depth64, force_mode=6), decode 1.1 c.
3. **Тюнинг матч-файндера на fb2 (mode 3 forced)**: max-preset 12.39 МиБ →
   block1M win1M d256 = 10.48 МиБ; block4M win4M d128 = 10.74; block2M d128 = 10.81.
4. **Bugfix-история mode 4** (все найдены точной диагностикой): знаковый wrap в
   prob4_step (1u-отравление тернарника), 2-битный декодер тегов (порядок бит),
   node-мismatch второго бита тега, гранулярность ротора lane (символ vs бит),
   sidx[1] в цикле байтов прогона, two-pass энкодер (обратный rANS + прямая модель),
   force_mode 5/6 писал mode-байт без учёта фактического вида payload.

## Честный вывод по «превзойти лучший алгоритм»
- Энтропия НЕ является узким местом на тексте: static order-0 (mode 3) ≈ оптимум для
  текущего потока токенов (модель: static 257 КБ vs adaptive 307 КБ на 1 МиБ fb2 при
  win256K; адаптивные extra-биты дистанций почти равномерны → сырой размер).
- mode 4 даёт −1.8% на fb2 (12.91 vs 13.15 при равных настройках), на коде проигрывает.
- Узкое место — **матч-файндер/парсер** (у xz окно на весь файл). Глубина цепочек и
  большие блоки дают −13…15%; rolling tails добавляют cross-block. Текущий пол:
  fb2 ≈ 10.5–11.5 МиБ против xz-6 8.0, zstd-19 7.95.
- На периодических данных и pack STENO уже выигрывает у всех (2.05% vs gzip 100%;
  pack −69%).
